# Повторный аудит текущего кода — 28 октября 2026

**Статус:** B1–B6 и O1–O2 исправлены. Реализация и актуальные проверки описаны
в [отчёте исправлений](fixes-2026-10-28.md). Ниже сохранено исходное описание
проблем до исправления.

Это новые замечания к текущему рабочему дереву, включая незакоммиченные
изменения. Перечни исправлений из двух предыдущих аудитов не повторяются.
Исправления в рамках этой проверки не вносились.

Прочитаны все основные Rust-модули — около 18,3 тысячи строк, — сборка,
PowerShell-скрипты, CI и связанные проверки. Найдены шесть ошибок и два
конкретных места для упрощения. Три ошибки воспроизведены отдельными тестами;
ещё три установлены по порядку вызовов и обработке ошибок в коде.

## Ошибки

### B1 · P1 · Поздний запрос AEA-ключа блокируется передачей самого образа

Код: `src/restore/file_data.rs:65–87`, `src/mux/stream.rs:174–187`.

`write_chunk` сначала вызывает `flush_pending`, который выполняет блокирующий
`MuxStream::write_all`, и только затем проверяет входящий запрос ключа.
Если Mac отправляет `StreamedImageDecryptionKey` и закрывает окно приёма
образа до получения ключа, mux успевает принять запрос в буфер канала,
но продолжает ждать открытия окна внутри `write_all`. До `exchange_keys`
управление не доходит. Это происходит и при отдельном DataPort для ответа
на запрос: этот порт некому открыть, пока занят тот же FileData worker.

Воспроизведение: подставной USB-транспорт выдаёт корректный запрос ключа
после начала передачи и объявляет нулевое окно. Ключ уже имеется в памяти;
сеть не нужна. Соединение с отдельным портом ответа не начинается. Тест
принудительно отменяет сессию после наблюдения зависания; штатный код
продолжал бы ждать тайм-аут окна 300 секунд.

Исправление: обеспечить обработку входящего запроса ключа во время ожидания
окна. Проверки только до или после большого блокирующего `write_all`
недостаточно. `exchange_keys` также не должен требовать предварительно
дописать весь образный буфер в уже закрытое окно.

### B2 · P2 · Завершение GUI-задачи может потерять последнюю ошибку журнала

Код: `src/gui/worker.rs:179–187`, `src/gui/events.rs:136–162`.

`pending_logs` возвращает пустой Vec как при пустой очереди, так и при
занятом mutex журнала. После получения Finished метод `poll` не различает
эти случаи и сразу извлекает Job из App. Записи, оставшиеся в
`Journal.pending`, больше не переносятся в видимую историю.

Воспроизведение: в очередь добавляется последняя ERROR-запись; другой поток
удерживает mutex 500 мс; в App поступает Finished. После `poll` запись
отсутствует в журнале GUI. Файл журнала может оставаться полным — ошибка
касается видимой истории, Copy и её использования как резервной копии.

Дополнительно тот же `poll` затем блокируется в `job.record`, ожидая mutex
и синхронный flush. Таким образом, неблокирующее чтение очереди само по себе
не обеспечивает отзывчивость интерфейса в момент завершения.

Исправление: различать «очередь прочитана» и «журнал занят» и завершать Job
после успешного переноса последних записей. Окончательную запись и flush
следует завершать вне потока отрисовки до уведомления о готовности результата.

### B3 · P2 · Потоковый verify ошибочно отвергает поздний вложенный FTAB

Код: `src/ipsw/verify.rs:79,123–143`, `src/firmware/containers.rs:165–174`.

Диапазоны для проверки digest определяются один раз по первому блоку
размером 2 MiB. Рекурсивный поиск рассматривает вложенный контейнер только
если его начало попало в этот блок. Если вложенная FTAB-таблица начинается
позже, digest её внутреннего payload вообще не вычисляется.

Воспроизведение: корректный внешний FTAB содержит блок 3 MiB и следующий
за ним вложенный FTAB с payload rkos. Проверка с полным содержимым успешно
подтверждает SHA-256 payload. Тот же файл через EntryDigests::verify
возвращает `manifest digest mismatch`. Обе проверки используют действующий
код проекта; повреждённых данных в фикстуре нет.

Исправление: извлекать необходимые индексы вложенных контейнеров по их
реальным смещениям либо обнаруживать их по мере чтения. Простое увеличение
первого блока лишь сдвигает границу ошибки. Проверка целиком и потоковая
проверка должны получать одинаковый набор диапазонов digest.

### B4 · P2 · Недостаток временного места обнаруживается после StartRestore

Код: `src/restore.rs:103–112`, `src/restore/session.rs:276–287`,
`src/restore/images.rs:13–30`.

Для Deflated OS-образа требуется временный файл полного распакованного
размера. Наличие места проверяется только в `serve_asr`, при обработке
запроса устройства. К этому моменту уже загружены boot-компоненты, запущен
restoreOS и отправлен StartRestore. Например, IPSW лежит на внешнем диске,
а системный том с TEMP почти заполнен: предсказуемый локальный отказ
возникает уже после начала восстановления.

Это установлено по порядку вызовов; физическое стирание устройства не
проверялось и не утверждается как неизбежное следствие этого сценария.

Исправление и упрощение: подготовить сжатый OS-образ до загрузки iBSS,
одновременно проверив CRC и сохранив результат распаковки для ASR. Сейчас
`verify_filesystem` распаковывает его в пустоту, а `serve_asr` повторно
распаковывает в файл. Одна ранняя подготовка убирает повторную декомпрессию
и позволяет обнаружить ошибку диска до изменения состояния Mac.

### B5 · P2 · Ошибка одного USB-устройства скрывает остальные устройства

Код: `src/usb.rs:90–103,225–238`, `src/gui/events.rs:37–52`.

`detect` прекращает весь обход через `?`, если у одного кандидата не удалось
прочитать или разобрать serial. GUI в этом случае очищает весь список
устройств, включая исправный выбранный Mac.

`RecoveryUsb::open(ecid)` также может остановиться на чужом устройстве:
если его serial не закэширован или не разобрался, ошибка открытия или чтения
возвращается до проверки ECID. Целевой Mac, находящийся дальше в списке,
не рассматривается. Условие возникает, например, при нескольких Mac и
отключении одного из них между перечислением и открытием.

Это установлено по обработке ошибок; физический сценарий с двумя Mac не
выполнялся.

Исправление: сохранять диагностику отдельного кандидата и продолжать обход;
если целевой ECID уже установлен, сохранять его конкретную ошибку для
итогового результата. Ошибку общего перечисления USB по-прежнему следует
возвращать целиком.

### B6 · P2 · Сбой постороннего каталога блокирует подходящую прошивку

Код: `src/catalog.rs:138–149`.

`latest` требует успешной загрузки и разбора обоих каталогов: macOS и
bridgeOS. `resolve_catalogs` вызывается только после этого. Поэтому ошибка
HTTP, тайм-аут или повреждённый ответ bridgeOS блокирует выбор Apple Silicon
прошивки даже при уже полученном подходящем macOS-каталоге. Обратная
зависимость действует для T2.

Это установлено по последовательности вызовов и ранним возвратам `?`;
проверка не вызывала реальный отказ сервисов Apple.

Исправление: обрабатывать результаты каталогов отдельно. Если доступный
каталог дал однозначный подходящий Release, сбой другого следует показывать
как диагностику. Проверку конфликтов между успешно полученными каталогами
нужно сохранить. Если подходящего результата нет, возвращать исходные
причины отказов.

## Конкретные упрощения

### O1 · GUI получает Release, но операция заново делает весь подбор

Код: `src/gui.rs:273–296`, `src/gui/setup.rs:122–136`,
`src/operations.rs:31–40,79–84`, `src/catalog.rs:156–178`.

GUI хранит FirmwareSelection с уже найденным Release и отдельным request id.
Однако Download и автоматический Restore/Revive этот результат не используют:
они снова вызывают `catalog::obtain → latest`. Один обычный путь
«показать прошивку → скачать» делает четыре запроса каталогов, и результат
предварительного показа не привязан к фактически скачиваемому Release.

Можно передавать выбранный Release в операцию и использовать существующий
`ensure_cached`; явный Retry обновляет выбор. Для CLI без предварительного
выбора остаётся текущий путь obtain. Глобальный кэш и новый сервис каталогов
для этого не нужны.

### O2 · tss_agent создаёт полноценный лишний HTTP Agent ради Config

Код: `src/net.rs:29–50,61–85`.

Сначала `agent_with_body_timeout` создаёт Agent и регистрирует его shutdown
в текущем Context. Затем `tss_agent` использует только `tss.config().clone()`,
создаёт второй Agent с нужным connector и регистрирует второй shutdown.
Первый Agent никогда не отправляет запросы, но его копия остаётся в списке
обработчиков отмены до завершения операции. Это повторяется на каждом TSS
запросе.

Достаточно строить Config до создания Agent и регистрировать отмену только
для используемого экземпляра. Разделение доверия TSS и HTTPS-прокси нужно
сохранить; замечание касается лишнего экземпляра клиента, а не TLS-проверок.
