# Остановка USB-интернета после Stall

В `restore-1792899664046367100.log` раздача включена в 00:14:42.552
без ограничения времени. В 00:24:36.345 Mac успешно обновил DHCP.
В 00:25:02.896 завершилось чтение USB с ошибкой `endpoint stalled`.
Следующая строка `session` сообщает о той же ошибке, а не о втором сбое.
Восстановление macOS к этому моменту уже завершилось.

В `share` нет таймера простоя: отсутствие пакетов оставляет чтения в
очереди. Прежде любая ошибка чтения выходила из `share` через `?`.
Затем `Link::drop` выключал приём Ethernet и возвращал data interface
в alternate setting 0. Именно это завершало раздачу после первого Stall.

В используемой nusb 0.2.8 на Windows `ERROR_GEN_FAILURE` преобразуется
в `TransferError::Stall`. Сам текст ошибки не доказывает сон Mac,
энергосбережение Windows или неисправность кабеля; журнал не содержит
данных, позволяющих выбрать одну из этих причин.

Теперь при Stall на bulk IN/OUT программа отменяет и забирает оставшиеся
завершения данного канала, вызывает `clear_halt` (WinUSB ResetPipe на
Windows) и продолжает работу. Для IN заново заполняется очередь чтений;
для OUT повторяется тот же буфер. Если сбой случился при отправке
завершающего нулевого пакета, повторяется только этот пакет.
Маршрутизатор и его TCP-соединения при этом не пересоздаются.

Для каждого направления допускаются три попытки восстановления подряд.
Успешная передача или пять секунд без новых попыток сбрасывают счётчик:
редкие сбои не накапливаются за часы простоя. Постоянный Stall,
неудачный ResetPipe и остальные ошибки по-прежнему завершаются ошибкой.

Порядок восстановления соответствует документации
[nusb clear_halt](https://docs.rs/nusb/0.2.8/nusb/struct.Endpoint.html#method.clear_halt)
и [Microsoft USB pipe recovery](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/how-to-recover-from-usb-pipe-errors).
Обычное ожидание пакетов не отменяется и не превращается в ошибку.
